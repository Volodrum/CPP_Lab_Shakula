# CrossApp — лабораторна робота 5

> Актуальний опис проєкту (лабораторна 6) — у [README.md](README.md). Сценарій лабораторної 5 з тижня 6 запускається з ключем `--service`: `dotnet run --project src/Cli -- --service [--file] [--cache]`.

## Лабораторна робота 5. Сервісний шар: інтерфейси, два сховища, ручний DI

**Мета**: забезпечити незалежність доменної логіки від способу зберігання даних: визначити абстракцію сховища (інтерфейс), розробити дві взаємозамінні реалізації і вибирати потрібну в точці входу без DI-контейнера.

**Варіант (бібліотека)**: `IBookStore` + `LendingService`; операції `AddBook` / `IssueCopy` / `ReturnCopy`; файлова реалізація тримає видання і примірники (а також видачі) в одному списку DTO.

### Запуск

| Команда | Що відбувається |

### 2. Домен, головна сутність і контракт сховища

Головна сутність процесу — **`Loan`** (видача примірника читачу). Вона посилається на **`BookCopy`** (фізичний примірник), а примірник через ISBN — на **`Book`** (видання). Усі три сутності з лабораторної 4 реалізують маркерний інтерфейс `ILibraryEntity { string Id { get; } }`, тож одне сховище тримає їх у спільному наборі з унікальним `Id`.

```csharp
namespace Core.Abstractions;

public interface IBookStore
{
    IReadOnlyList<T> List<T>() where T : class, ILibraryEntity;
    T? GetById<T>(string id) where T : class, ILibraryEntity;
    void Add(ILibraryEntity item);
    void Update(ILibraryEntity item);
    bool Remove(string id);
}
```

| Метод | Чому саме він |
| :---- | :------------ |
| `List<T>()` | Сервісу потрібні всі видачі читача (ліміт 5), примірники видання, каталог для виводу. `IReadOnlyList` — щоб зовнішній код не додав запис в обхід `Add`. `T` обирає тип сутності, тож не треба трьох методів `ListBooks/ListCopies/ListLoans`. |
| `GetById<T>(id)` | `IssueCopy` шукає примірник, `ReturnCopy` шукає видачу. `T?` — бо запису може не бути (або він іншого типу), і це нормальний результат пошуку. |
| `Add(item)` | `AddBook`, `RegisterCopy`, `IssueCopy` створюють нові записи. Унікальність `Id` перевіряє саме сховище (умова щодо набору записів, а не однієї сутності). |
| `Update(item)` | Після `copy.Issue()`, `loan.Close()`, `loan.MarkLost()` стан сутності треба зберегти — для файлу це запис на диск. |
| `Remove(id)` | `RemoveBook`: вилучити з каталогу видання без примірників (помилково заведене). |

Методів «про запас» (`Count`, `Clear`, `SaveToFile`, `Flush`) немає: кожну з них довелося б реалізувати в усіх сховищах, а сервісу вони не потрібні.

**Операції сервісу** (`LendingService`, мінімум варіанту — `AddBook` / `IssueCopy` / `ReturnCopy`):

| Операція | Правило на рівні сервісу (на кілька сутностей) |
| :------- | :--------------------------------------------- |
| `AddBook(isbn, title, year, author)` | ISBN унікальний у каталозі (`978-0-13-235088-4` = `9780132350884`) |
| `RegisterCopy(isbn)` | Примірник можна зареєструвати лише для наявного видання |
| `IssueCopy(copyId, readerId, date)` | Примірник існує; у читача менше 5 незакритих видач |
| `ReturnCopy(loanId, date)` | Видача існує; `Loan.Close` сам повертає примірник на полицю |
| `ReportLost(loanId)` | Видача існує; перехід стану перевіряє `Loan` |
| `RemoveBook(bookId)` | У видання немає примірників |
| `All<T>()`, `Find<T>(id)`, `Search<T>(Func<T,bool>)`, `FindByIsbn`, `CopiesOf`, `CountActiveLoans` | Читання |

Інваріанти однієї сутності (порожній ISBN, рік із майбутнього, повторна видача виданого примірника тощо) не дублюються ні в сервісі, ні в сховищах — їх перевіряють `Book.Create`, `BookCopy.Issue`, `Loan.Open/Close` з лабораторної 4.

### 3. Дві реалізації

|  | `InMemoryBookStore` | `FileBookStore` |
| :-- | :-- | :-- |
| Де дані | `Dictionary<string, ILibraryEntity>` (ключі без урахування регістру) | Той самий словник як кеш + файл JSON |
| Початкові дані | `SampleData.Items()` через конструктор (`IEnumerable<ILibraryEntity>? seed = null`) | Те, що лежить у файлі; якщо файлу немає — порожньо |
| Читання | Зі словника | Перше звернення читає файл (`EnsureLoaded`), далі — з кешу |
| Зміна | Лише словник | Словник + `Flush()` (перезапис файлу) після **кожного** `Add` / `Update` / `Remove` |
| Після виходу | Дані зникають | Дані лишаються, наступний запуск їх бачить |
| Дубль id | `InvalidOperationException` | `InvalidOperationException`; дубль у самому файлі — `InvalidDataException` |

**Шлях до файлу**: `Path.Combine(AppContext.BaseDirectory, "data", "library.json")` → `src/Cli/bin/Debug/net10.0/data/library.json`. Каталог створюється `Directory.CreateDirectory` перед записом; абсолютних шляхів у коді немає.

**Формат файлу**: один JSON-масив `LibraryItemDto`. Тип елемента — у полі `"kind"` (`[JsonPolymorphic]` + `[JsonDerivedType]` на `LibraryItemDto`). На диск ідуть DTO з тижня 3 (`BookDto`, `BookCopyDto`, `LoanDto`), а не сутності: у сутностей приватні конструктори й сетери, а мапінг роблять `ToDto()` / `FromDto()` з лабораторної 4. Під час завантаження спершу відновлюються видання й примірники, потім видачі: `Loan.FromDto(dto, copy)` отримує **той самий** об'єкт `BookCopy`, що лежить у кеші, тому стан видачі та примірника не розходиться. Кирилиця екранується (`\u0427...`) — це штатна поведінка `System.Text.Json`, її налаштування заплановано на тиждень 9.

### 4. Схема залежностей

```text
Cli (Program.cs + StoreFactory.cs)          ← composition root: єдине місце з new конкретних сховищ
  │ new LendingService(store)
  ▼
LendingService ──────► IBookStore           ← сервіс знає лише інтерфейс
                          ▲    ▲    ▲
          ┌───────────────┘    │    └────────────────┐
  InMemoryBookStore     FileBookStore     CachingBookStore ──► IBookStore (будь-яке інше)
                              │
                              ▼
                     LibraryItemDto (JSON)
```

`Core` не посилається на `Cli`; `LendingService` не згадує жодного класу зі `Storage`.

### 5. Composition root і вивід консолі

`src/Cli/Program.cs`:

```csharp
string dataPath = Path.Combine(AppContext.BaseDirectory, "data", "library.json");
IBookStore store = StoreFactory.Create(args, dataPath); // --file → FileBookStore, інакше InMemoryBookStore; --cache → декоратор

Console.WriteLine($"Сховище: {(store is CachingBookStore ? store.ToString() : store.GetType().Name)}");
```

`src/Cli/StoreFactory.cs` — тернарний вибір реалізації:

```csharp
IBookStore store = args.Contains("--file")
    ? new FileBookStore(dataPath)
    : new InMemoryBookStore(SampleData.Items());

return args.Contains("--cache") ? new CachingBookStore(store) : store;
```

```text
 C-76303070 [978-0-13-235088-4] — на полиці

=== Додаткове 2: пошук з Func<T, bool> ===
 Видання до 2000 року: 0
 Примірників на полиці: 4
 Втрачені примірники: немає
```

**Спостережуваний факт**: той самий `LendingService` і той самий сценарій дають два різні режими. У другому запуску видання `B-cfafeb67` знайдено у файлі (не створено вдруге), примірників стало 4, видач — 2. Сервіс при цьому не змінювався: змінився лише рядок вибору сховища.

### 6. Сценарій відмови

Винятки перехоплює Cli (`TryDo` у `Program.cs`, `catch (Exception ex) when (ex is InvalidOperationException or ArgumentException)`), друкується лише `Message`:

| Спроба | Хто відмовляє | Повідомлення |
| :----- | :------------ | :----------- |
| Видача неіснуючого примірника | `LendingService.IssueCopy` (`GetById ?? throw`) | `Немає примірника з id=C-404.` |
| Повернення неіснуючої видачі | `LendingService.ReturnCopy` | `Немає видачі з id=L-404.` |
| Повторна видача виданого примірника | `BookCopy.Issue` (лаб. 4) | `Примірник C-... вже виданий, повторна видача неможлива` |
| Дубль ISBN | `LendingService.AddBook` | `Видання з ISBN 978-0-13-235088-4 уже є в каталозі: B-...` |
| Дубль id | `IBookStore.Add` (обидві реалізації) | `Запис з id=B-... уже існує.` |
| Вилучення видання з примірниками | `LendingService.RemoveBook` | `Видання B-... має 2 примірн., вилучити його з каталогу неможливо.` |

Після всіх відмов стан не змінився: примірник так само виданий, у читача одна незакрита видача.

### 7. Додаткові завдання

#### 1. Декоратор `CachingBookStore`

Приймає будь-яке інше `IBookStore` у конструкторі й сам реалізує `IBookStore`: той самий контракт, нова поведінка. Читання (`List<T>`, `GetById<T>`) запам'ятовуються; зміни (`Add`/`Update`/`Remove`) завжди йдуть у внутрішнє сховище, після чого кеш за id оновлюється, а кешовані списки скидаються. `GetById` кешує сам запис, а не «запис типу T», тому промах `GetById<Book>("C-1")` не ховає примірник `C-1`. Лічильники `Hits`/`Misses` показують ефект:

```text
> dotnet run --project src/Cli -- --cache
Сховище: CachingBookStore → InMemoryBookStore
...
=== Додаткове 1: кеш — влучань 29, промахів 13 ===

> dotnet run --project src/Cli -- --file --cache
Сховище: CachingBookStore → FileBookStore
...
=== Додаткове 1: кеш — влучань 13, промахів 13 ===
```

Ні `LendingService`, ні `FileBookStore` для цього не змінювались. Для файлу виграш невеликий (`FileBookStore` і так тримає кеш), але на тижні 11 кожне читання з БД — це запит, і той самий декоратор без змін ляже поверх EF-сховища.

#### 2. Пошук з `Func<T, bool>`

```csharp
public IReadOnlyList<T> Search<T>(Func<T, bool> predicate) where T : class, ILibraryEntity
{
    ArgumentNullException.ThrowIfNull(predicate);
    return _store.List<T>().Where(predicate).ToList();
}
```

Умову передає викликач: `service.Search<Book>(b => b.Year < 2000)`, `service.Search<BookCopy>(c => !c.IsIssued)`, `service.Search<Loan>(l => l.Status == LoanStatus.Lost)`. На ньому ж побудовано `FindByIsbn` і `CopiesOf`. Метод живе в сервісі, а не в інтерфейсі: контракт сховища не розростається, і кожна реалізація не мусить вміти фільтрувати. Обмеження: `Func` виконується в пам'яті після `List<T>()`; для БД на тижнях 7/11 знадобиться `Expression<Func<T, bool>>`, щоб умова перетворилась на SQL.

#### 3. Фабрика `StoreFactory.Create(args, dataPath)`

| | «Усе в Program.cs» | `StoreFactory` |
| :-- | :-- | :-- |
| Де `new FileBookStore` | Прямо в `Program.cs` | У `StoreFactory.cs` (теж Cli) |
| `Program.cs` | Розбір аргументів + вибір + сценарій | Один рядок `StoreFactory.Create(args, dataPath)` + сценарій |
| Новий режим (`--cache`, на тижні 11 `--db`) | Ще одна гілка в `Program.cs` | Ще одна гілка у фабриці, `Program.cs` не змінюється |
| Повторне використання | Ні | Те саме правило вибору можна викликати з тестів або іншої точки входу |
| Наочність | Увесь граф об'єктів видно в одному файлі | Треба відкрити ще один файл |

Фабрику навмисно залишено в `Cli`, а не в `Core`: вона знає про конкретні класи і про аргументи командного рядка, тобто є частиною composition root. Якби вона була в `Core`, пошук `FileBookStore` у `src/Core` знайшов би не лише файл реалізації. Для двох-трьох реалізацій обидва варіанти рівноцінні; фабрика виграє, коли способів вибору стає більше (аргументи + конфігурація + змінні середовища).

### 8. Що зміниться на тижні 11 (база даних)

Додасться ще одна реалізація, наприклад `EfBookStore : IBookStore` на основі `DbContext`, і один рядок у `StoreFactory` (`--db` → `new EfBookStore(...)`). `LendingService`, `Book`/`BookCopy`/`Loan`, `InMemoryBookStore` і `FileBookStore` не зміняться. Що доведеться продумати: мапінг сутностей на таблиці (EF уміє працювати з приватними сетерами, або ж залишимо DTO як моделі таблиць); зв'язок `Loan → BookCopy` стане зовнішнім ключем; `List<T>()` і `Search` з `Func` вантажать усе в пам'ять, тож для великих таблиць у контракт або сервіс прийде `Expression<Func<T, bool>>`; «запис після кожної зміни» замінить `SaveChanges`, а пара `Add(loan)` + `Update(copy)` в `IssueCopy` має виконуватись в одній транзакції. На тижні 10 з'явиться контейнер DI в Api — він замінить `StoreFactory`, а не сервіс.

### 11. Відповіді на питання на захисті

1. **Що таке composition root і де він у вашому проєкті?** Єдине місце, де створюються конкретні об'єкти та з'єднуються між собою. У мене це `src/Cli/Program.cs` (`new LendingService(store)`) разом із `src/Cli/StoreFactory.cs` (`new FileBookStore` / `new InMemoryBookStore` / `new CachingBookStore`).
2. **Чому сервіс не створює сховище сам?** (1) Тестованість: у тест можна передати `InMemoryBookStore` замість файлу. (2) Заміна сховища (файл → БД) і зміна конфігурації (шлях до файлу) не потребують змін у сервісі. Третій наслідок — декоратор `CachingBookStore` можна вставити без відома сервісу.
3. **Dependency Inversion vs Dependency Injection?** Inversion — принцип проєктування: високорівневий `LendingService` і низькорівневий `FileBookStore` обидва залежать від абстракції `IBookStore`. Injection — техніка: готову залежність передають ззовні (у мене через конструктор). DIP каже, *від чого* залежати, DI — *як* залежність потрапляє в об'єкт.
4. **Чому `List()` повертає `IReadOnlyList`, а не `List`?** Щоб викликач не міг зробити `store.List<Loan>().Add(...)` і змінити дані в обхід `Add` (без перевірки дубля id та без запису у файл). До того ж `InMemoryBookStore` і `FileBookStore` повертають копію (`ToList()`), а `CachingBookStore` — обгортку `AsReadOnly()`, тож змінити дані сховища через результат `List<T>()` неможливо.
5. **Що зміниться в сервісі, коли сховищем стане БД?** Нічого в коді `LendingService`: зміниться лише рядок у composition root. Можливі зміни — лише якщо знадобляться нові можливості (транзакція на `IssueCopy`, `Expression` для пошуку) — див. розділ 8.
6. **Навіщо DTO між файлом і сутністю?** Сутності мають приватні конструктори й сетери, `System.Text.Json` їх не заповнить без обходу інкапсуляції. DTO — відкритий формат, а `FromDto` проганяє дані з файлу через ті самі перевірки, що й створення; пошкоджений файл не дасть некоректного об'єкта. Формат файлу можна міняти, не чіпаючи домен.
7. **Скільки методів має бути в інтерфейсі?** Стільки, скільки потрібно сервісу — у мене 5. Кожен «про запас» метод доведеться реалізувати в усіх сховищах (зараз їх три, на тижні 11 — чотири), і більшість реалізацій будуть заглушками.
8. **Як перевірити сервіс тестом, не торкаючись диска?** `var service = new LendingService(new InMemoryBookStore(SampleData.Items()));` — і викликати `IssueCopy`, `ReturnCopy` тощо, перевіряючи результат через `service.Find<T>` або сам store.
9. **Чому `FileBookStore` кешує дані?** Читати й розбирати весь JSON на кожен `GetById` дорого; крім того, без кешу кожне читання створювало б нові об'єкти, і `Loan.Copy` вказував би не на той `BookCopy`, що повернув `GetById`. Кеш дає один об'єкт на id і читає файл лише раз.
10. **Чи потрібен контейнер DI у консольному застосунку?** Тут — ні: граф із трьох об'єктів збирається двома рядками `new`, усе видно в одному місці, і нема потреби в часі життя (scoped/singleton). Контейнер виправданий у Api (тиждень 10), де об'єкти створюються на кожен запит, а залежностей багато.

### 12. Що змінилося в коді попередніх лабораторних

- `LendingService` (лаб. 4) більше не тримає `List<Loan>`: видачі й примірники лежать у сховищі, ліміт видач рахується через `IBookStore.List<Loan>()`; id генеруються через `Guid`. `DomainDemo` отримує сервіс із `Program.cs`, тому id у її виводі тепер випадкові, а сценарії ті самі.
- Імпорт лабораторної 3 перенесено з `Program.cs` у `ImportDemo.cs` без зміни логіки: `--import [шлях]` або просто шлях до файлу (`dotnet run --project src/Cli -- data/mixed.csv`).
- `LibraryItemDto` отримав атрибути `[JsonPolymorphic]`/`[JsonDerivedType]`; імпорт `List<BookDto>` з JSON (лаб. 3) на це не реагує.
- `Book.HasIsbn` порівнює ISBN без урахування дефісів (`IsbnRules.Compact`).
